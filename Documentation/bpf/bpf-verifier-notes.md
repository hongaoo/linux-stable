# BPF verifier 补充说明

这份文档用来补充主文档里关于 verifier 的部分。它的目标不是复述 `verifier.rst` 的所有细节，而是把 verifier 放回 BPF 整体架构里，解释它到底在解决什么问题，以及为什么它几乎决定了 Linux BPF 的实际能力边界。

## 1. verifier 先解决的不是“优化”，而是“能不能让不可信程序进内核”

如果只看 ISA，BPF 像一台寄存器虚拟机；但如果没有 verifier，它就仍然只是一个危险的内核字节码执行器。

verifier 的根本任务是：

- 证明程序会在受控边界内执行
- 证明程序不会越界访问内存
- 证明程序不会把本来有类型约束的指针当普通整数乱用
- 证明 helper / kfunc 的调用参数满足约束

所以 verifier 的角色不是“额外加的一层安全插件”，而更像 Linux BPF 语言语义的一部分。

在 Linux 里，一段 BPF 程序是否成立，不只取决于它是不是合法字节码，也取决于 verifier 能不能证明它安全。

## 2. verifier 大致做两类事

从主线理解，可以把 verifier 的工作粗略分成两类：

### 2.1 控制流检查

这一层主要回答：

- 程序有没有非法控制流
- 有没有不可达指令
- 控制流图是否满足 verifier 的基本要求

这部分可以理解成“先确认程序结构本身没有坏掉”。

### 2.2 状态模拟

这一层才是 verifier 最核心的部分。

它会沿着可能的执行路径去模拟寄存器和栈状态变化，并持续追踪：

- 某个寄存器当前是未初始化、标量还是指针
- 这个指针到底指向什么对象
- 这个对象允许做什么偏移和访问
- 栈上的哪些字节已经初始化
- 某个条件分支之后，某个值的范围会不会被缩小

也就是说，verifier 不是只检查“这条指令是不是存在”，而是在检查“这条指令在当前状态下是否安全”。

## 3. 为什么说 verifier 是 BPF 的真正能力边界之一

很多时候，一个能力是否能被 BPF 使用，不是由 ISA 单独决定的，而是由“verifier 能否证明这种使用方式安全”决定的。

例如：

- 不是所有指针都能做任意算术
- 不是所有 helper 都能接受任意来源的指针
- 不是所有栈上的数据在写入前都可读
- 不是所有 map 返回值在未判空之前都能直接解引用

这说明 Linux BPF 的实际能力边界，本质上是三者共同作用的结果：

- ISA 提供表达能力
- verifier 约束安全边界
- program type / helper / kfunc 定义可用语义

## 4. verifier 在跟踪什么

理解 verifier，最重要的是接受一个事实：**寄存器在 verifier 看来不仅仅存“值”，还存“类型和范围信息”**。

在一个简化视角里，寄存器可能处在几种关键状态：

- 未初始化
- 普通标量值
- 指向上下文的指针
- 指向 map 的指针
- 指向 map value 的指针
- 指向栈的指针
- 指向包数据的指针
- 可空对象指针

这意味着同一条加法指令，对不同寄存器状态的含义完全不同：

- 对标量做加法通常是允许的
- 对某些受限指针做加法可能会丢失类型信息
- 对某些指针做不被允许的运算会直接导致验证失败

所以 verifier 不是在“解释一套无类型汇编”，而是在“验证一套带对象语义的受限低级语言”。

## 5. verifier 为什么特别关心栈

栈是 verifier 非常敏感的区域，因为它既是局部状态存储区，也是很多 helper 调用参数的中转区。

verifier 对栈至少关心三件事：

- 访问是否越界
- 读取之前是否已经写过
- 某块栈内存当前保存的是普通字节还是带对象语义的数据

这也是为什么 BPF 程序里一个常见错误是：

- 明明地址落在栈范围内
- 但因为这块区域还没初始化，读取仍然会被 verifier 拒绝

从这个角度看，verifier 验证的不是“地址看起来对不对”，而是“该次读取在程序状态上是否有定义”。

## 6. verifier 为什么特别关心指针

Linux BPF 里很多关键能力都依赖“受约束的对象指针”：

- context 指针
- map value 指针
- socket/task 等内核对象指针
- packet data 指针

这些指针不是普通整数，不能想怎么算就怎么算。原因很简单：

- 一旦允许随意算术和随意转型，verifier 就很难再证明访问边界
- 一旦边界证明失效，BPF 对内核来说就不再安全

所以 verifier 会尽量保留“这是一个什么对象的指针”这层信息；一旦程序做了某些不被允许的操作，就可能把它降级成普通标量，随后失去原本允许的访问能力。

## 7. 条件分支为什么对 verifier 很重要

verifier 不只关心你写了什么判断，还关心判断之后能推导出什么新事实。

例如某个可空指针：

- 在判空之前，不能安全解引用
- 在判空之后，某个分支里它可能就能从“可空指针”收窄成“非空有效指针”

类似地：

- 某个长度值在比较之前范围很宽
- 经过边界检查后，后续访问就可能被认为是安全的

也就是说，条件分支不仅影响运行时逻辑，也影响 verifier 对程序状态的静态推理结果。

## 8. helper 和 kfunc 为什么也要受 verifier 约束

helper / kfunc 不是“调用了就行”的普通函数。它们能否被调用、参数能否被接受、返回值是否可以继续使用，都要经过 verifier 参与判断。

原因在于：

- 某些 helper 只能接受特定类型的指针
- 某些 kfunc 需要 trusted pointer
- 某些返回值必须先判空
- 某些对象带引用语义，必须在程序结束前释放

从架构上看，ABI 解决的是“调用形式统一”，而 verifier 解决的是“这次调用在当前状态下是否合法”。

## 9. verifier 和 program type 的关系

verifier 不是完全独立于 program type 的。

program type 决定很多基础语义：

- R1 初始时是什么 context
- 允许访问 context 的哪些字段
- 允许使用哪些 helper / kfunc
- 返回值在这个类型里表示什么动作

所以 verifier 不是面对“抽象 BPF 程序”做统一验证，而是在“某个具体 program type 的语义上下文里”做验证。

这也是为什么同样一段逻辑，放到不同 program type 下，可能可验证性完全不同。

## 10. verifier 和 JIT 不是替代关系

很多初学者会把 verifier 和 JIT 放在一起理解，但它们职责完全不同：

- verifier 证明程序安全
- JIT 把已通过验证的程序翻译成目标架构机器码

JIT 关心性能和映射；verifier 关心安全和正确性边界。

在执行链条上，更合理的理解是：

1. 程序先经过 verifier
2. 通过后再交给解释器或 JIT 执行

所以 verifier 是执行前的“合法性证明”，不是执行时的加速器。

## 11. 为什么说 verifier 影响写法，而不只是影响能否加载

verifier 的存在不仅影响“程序最后能否通过”，还会反过来塑造 BPF 程序的常见写法。

例如很多 BPF 程序都有这些习惯：

- 先做边界检查再访问包数据
- 先判空再使用 map lookup 结果
- 调 helper 前先把关键值保存到 R6-R9 或栈
- 用更清晰的控制流帮助 verifier 收窄状态范围

这些不是风格问题，而是 verifier 驱动出来的编程模式。

也就是说，verifier 不只是审查者，它还在事实上塑造 Linux BPF 的代码风格和表达方式。

## 12. 读 verifier 文档时最值得抓住的主线

如果你去读 `verifier.rst`，最值得抓住的不是所有细节枚举，而是这条主线：

> verifier 在沿着所有可能路径，持续证明“当前寄存器/栈/指针状态下，接下来的每一步访问和调用都安全”。

只要把这条主线抓住，后面看到：

- 指针类型
- 标量范围
- 判空之后的状态收窄
- 栈初始化要求
- helper 参数约束

这些内容都会更容易串起来。

## 13. 一句话压缩版

如果把 verifier 压成一句话，可以这样记：

> verifier 是 Linux BPF 的静态安全证明器，它不是简单检查字节码是否合法，而是在具体 program type 的语义上下文里，证明寄存器、栈、指针、边界访问和 helper/kfunc 调用在所有可达路径上都安全。
