# BPF ABI 补充说明

这份文档专门补充主文档里“寄存器与调用约定 ABI”那一节，重点解释 BPF ABI 在工程上到底意味着什么，以及它为什么是 BPF 从“过滤规则”演进成“受限执行模型”的关键条件之一。

## 1. 先把 ABI 放回正确语境

这里的 ABI 不是用户态程序常说的 glibc ABI，也不是系统调用 ABI，而是 BPF 虚拟机自己的运行时约定。

它规定的是：

- 寄存器如何分工
- 函数参数如何传递
- 返回值写到哪里
- 哪些寄存器调用后必须保持
- 栈如何访问
- 调用发生后寄存器状态如何变化

如果没有这套约定，BPF 指令虽然仍然可以执行，但程序之间、程序与 helper 之间、以及程序与 JIT 之间就很难形成稳定配合。

## 2. 最重要的一张表：R0 到 R10

先记住这一版即可：

| 寄存器 | 含义 | 作用 |
| --- | --- | --- |
| R0 | 返回值寄存器 | helper 返回值、子程序返回值、程序 EXIT 返回值 |
| R1-R5 | 参数寄存器 | 向 helper、kfunc、BPF 子程序传参 |
| R6-R9 | callee-saved | 用来跨调用保存局部状态 |
| R10 | 只读帧指针 | 作为 BPF 栈访问基准 |

这一布局有一个非常明确的目的：让“调用”成为 BPF 的一等能力，而不是执行过程中临时拼出来的技巧。

## 3. caller-saved 和 callee-saved 在 BPF 里怎么理解

### 3.1 caller-saved

在 BPF 的常见理解里，R0-R5 属于更接近 caller-saved 的寄存器集合。

直觉上可以这样记：

- R1-R5 主要用来传参
- 一次调用完成后，调用方不应该再指望它们保留原值
- 如果调用前这些寄存器里有之后还要继续用的值，就必须先搬到 R6-R9 或栈上

这也是为什么很多 BPF 程序在调用 helper 前会先把关键上下文或中间结果保存到 R6-R9。

### 3.2 callee-saved

R6-R9 是 callee-saved，可以理解为“跨调用保持稳定的工作寄存器”。

这几个寄存器的重要性非常高，因为 BPF 一边要调用 helper/kfunc，一边又不能像普通 C 编译器那样随意拥有大量通用寄存器。因此，R6-R9 常常承担：

- 保存 context 指针副本
- 保存 map/value 指针
- 保存关键中间结果
- 在多次 helper 调用之间维持程序局部状态

## 4. 为什么 R10 是只读帧指针

R10 不是普通通用寄存器，而是只读帧指针。

这么设计有几个直接原因：

- verifier 需要一个稳定的栈基准点
- 程序不能随意移动栈顶，否则栈访问边界难以静态证明
- JIT 和解释器都需要一个统一、稳定的栈寻址模型

在 BPF 里，栈访问通常以 R10 为基准，并使用负偏移访问局部存储，例如概念上类似：

- R10 - 8
- R10 - 16
- R10 - 32

这种模型的好处是：栈布局更容易被 verifier 推理，也更容易对“哪些字节已经初始化、哪些字节可读、哪些访问越界”做静态判断。

## 5. 一次 helper 调用前后，寄存器会发生什么

从理解程序行为的角度，可以把一次 helper 调用简化成下面的模型：

1. 调用前，把参数放进 R1-R5
2. 执行调用
3. 返回值写入 R0
4. R1-R5 不再保证保留原值
5. R6-R9 仍然有效

这意味着一个很重要的编程习惯：

- 如果当前 context 指针或某个关键指针后面还要继续使用，不要只留在 R1-R5 里
- 应该尽早保存到 R6-R9 或栈上

这也是 verifier 文档里反复强调的一类模式：helper 调用会改变寄存器可用状态，因此程序必须显式管理自己的活跃值。

## 6. helper、kfunc 和 BPF 子程序在 ABI 上有什么共同点

虽然三者在语义上不同，但从调用约定角度看，有一个共通主线：

- 参数仍然按寄存器约定传递
- 返回值仍然回到 R0
- 调用边界两侧都依赖同一套寄存器分工

不同点主要不是“参数寄存器换了一套”，而是：

- verifier 对参数类型的要求不同
- helper/kfunc 的安全约束不同
- 某些对象指针是否允许传递、是否必须 trusted、是否允许为 NULL，这些规则不同

所以 ABI 解决的是“怎么调用”，而 verifier 与对象模型解决的是“能不能这么调用”。

## 7. 为什么这套 ABI 对 JIT 很重要

如果 BPF 没有稳定 ABI，那么 JIT 每次处理调用都需要做更多适配工作：

- 参数摆放方式不固定
- 返回值位置不固定
- 跨调用寄存器保存规则不固定

这样会直接增加：

- 指令搬运开销
- JIT 实现复杂度
- 出错概率

而 BPF 之所以能高效映射到真实 CPU，一个关键前提就是它从一开始就把寄存器职责和调用规则固定下来。这样 JIT 可以更直接地把 BPF 寄存器映射到目标架构寄存器，并围绕固定的调用协议生成代码。

## 8. 为什么说 ABI 让 BPF 不再只是“过滤规则”

没有 ABI 的过滤模型通常更像：

- 输入进来
- 若干指令顺序执行
- 得到一个结果

而有了寄存器分工、调用规则和稳定栈模型之后，BPF 才真正具备：

- 组织局部状态
- 调用 helper / kfunc
- 组织子程序
- 在多次调用之间保持关键值
- 表达更复杂的控制流

因此，ABI 的意义不只是“规定参数放哪”，而是给 BPF 提供了一个足够稳定的程序结构基础。

## 9. 读文档时最容易混淆的几点

### 9.1 ABI 不等于 Linux 用户态 ABI

这里讨论的是 BPF 机器自己的 ABI，不是进程调用 libc 函数时的 ABI，也不是系统调用编号和参数布局。

### 9.2 ABI 不等于 verifier 规则

ABI 规定调用形式；verifier 规定调用是否合法。

例如：

- ABI 可以规定参数从 R1-R5 传
- 但 verifier 才会进一步判断 R1 里这个指针是不是合法类型，R2 这个长度是不是可信，R3 是否可能为 NULL

### 9.3 ABI 不等于 program type

ABI 在不同 BPF 程序里是共用的，但不同 program type 决定：

- R1 一开始到底指向什么 context
- 返回值的业务含义是什么
- 当前程序能调用哪些 helper / kfunc

所以它们是三层不同问题：

- ABI：调用规则
- verifier：安全约束
- program type：执行语义

## 10. 一句话压缩版

如果把 BPF ABI 压成一句话，可以这么记：

> BPF ABI 就是 BPF 虚拟机内部关于“寄存器怎么分工、函数怎么传参和返回、栈怎么访问、调用后哪些值还能继续信赖”的统一规则。

而这套规则的价值，在于它同时服务了程序组织、helper/kfunc 调用、verifier 推理以及 JIT 映射。
