# BTF 与 CO-RE 补充说明

这份文档补充主文档里 BTF、CO-RE 和加载流程相关的部分。重点不是穷举 BTF 格式细节，而是解释：为什么 BTF 会成为现代 BPF 工程体系的关键支点，以及它和 libbpf、LLVM relocation、内核自描述能力之间是什么关系。

## 1. 先说一句最重要的话

如果把 BPF 程序只看成字节码，那么它只能回答“做什么”。

而 BTF 让系统开始知道：

- 程序里涉及的对象是什么类型
- 某个字段在什么结构里
- 某个函数或子程序的签名是什么
- 某些全局变量、数据段和代码位置应当如何解释

所以 BTF 的价值不只是“调试更方便”，而是给 BPF 增加了一层类型和结构语义。

## 2. BTF 本质上是什么

从文档定义看，BTF 是一种元数据格式，用来描述与 BPF 程序和 map 相关的调试/类型信息。

但从工程视角，更实用的理解是：

> BTF 是一份可被内核、libbpf、bpftool 和 verifier 共同消费的轻量级类型描述数据。

它既是：

- 用户态对象文件里的类型描述

也是：

- 内核运行时暴露出来的自描述类型数据库

这两者对上之后，BPF 程序才有机会跨内核版本保持更高的可移植性。

## 3. BTF 里大概有什么

从 `btf.rst` 的角度，BTF 至少包含两大基本部分：

- type section
- string section

其中 type section 里会编码很多类型和类型相关实体，例如：

- 整数
- 指针
- 数组
- struct / union
- enum
- typedef
- 函数
- 函数原型
- 变量
- 数据段

这意味着 BTF 已经不是“只有结构体字段表”的简单东西，而是一套可以描述程序对象关系的轻量类型系统。

## 4. 为什么说 BTF 不只是调试信息

如果只从传统编译器视角看，类型元数据很容易被归类成调试信息。

但在 BPF 里，BTF 的作用更强：

- 它帮助 loader 和内核理解对象布局
- 它支撑 CO-RE 重定位
- 它支撑 map pretty print
- 它支撑基于 BTF ID 的 helper / kfunc / 类型关联
- 它能改善 verifier log、反汇编和源码定位体验

所以 BTF 不是“顺便带上的调试附件”，而是现代 BPF 生态中的核心运行期辅助元数据。

## 5. CO-RE 到底解决什么问题

CO-RE 是 Compile Once, Run Everywhere。

它想解决的问题非常直接：

- 你在某个内核版本上编译出的 BPF 程序
- 不能因为目标机器上的结构体字段偏移变化、某些类型布局变化，就立刻失效

传统上，BPF 程序直接读内核结构体时，天然很脆弱，因为：

- 字段可能移动
- 成员顺序可能变化
- 某些配置项会影响布局

CO-RE 的目标不是消灭所有兼容性问题，而是把“同一逻辑因为字段偏移不同就无法运行”这类问题尽量转化成“加载时重定位修正”。

## 6. CO-RE 为什么依赖 BTF

CO-RE 并不是“神奇自动兼容层”，它依赖一条明确的数据链路：

1. 编译时，编译器在对象文件里记录程序使用了哪些类型和字段
2. 这些信息以 BTF 与相关 relocation 形式保留下来
3. 目标机器内核暴露自己的 BTF
4. libbpf 在加载时把两边对齐
5. 然后把需要修正的偏移和相关数据重定位到当前运行内核的实际布局

所以 CO-RE 的核心不是“运行时猜测结构体长什么样”，而是“利用两端的类型描述做匹配和重定位”。

## 7. libbpf 在这条链里做什么

主文档里已经提到 libbpf 负责 open / load / attach，但在 BTF/CO-RE 这件事上，它扮演的是中枢协调者。

它要做的事情包括：

- 解析 BPF ELF 对象
- 读取对象里的 BTF 和 relocation 信息
- 获取目标内核的 BTF
- 匹配程序类型和目标内核类型
- 把需要修正的字段偏移、类型相关引用和其它可重定位数据替换成当前内核可用的值

因此，从工程角度可以把 libbpf 看成：

> 把“编译期类型视图”翻译成“当前内核实际布局”的桥接器。

## 8. LLVM relocation 在这里扮演什么角色

`llvm_reloc.rst` 说明的是：LLVM BPF backend 会在 ELF 对象里记录不同种类的 relocation。

这件事的意义在于，编译器不会把所有地址/偏移都直接钉死，而是把“这里之后需要被解释或修正”这件事明确记录下来。

从主线理解，relocation 至少服务三类需求：

- 代码里的符号引用
- 调用目标定位
- 与 BTF / `.BTF.ext` 相关的数据修正

因此，LLVM relocation 提供的是“后续还能被 loader 重新解释和修正的挂点”。

而 libbpf 与 BTF 则决定“怎么修、按什么语义修”。

## 9. 为什么内核自己的 BTF 很关键

现代 BPF 开发里一个非常关键的事实是：运行中的内核可以通过 `/sys/kernel/btf/vmlinux` 暴露自身 BTF。

这意味着目标机器不需要只靠一堆匹配版本的内核头文件来描述自己，它可以直接提供一份更接近真实运行布局的类型视图。

从体系结构上看，这等于 Linux 内核开始具备一种“自描述能力”：

- 我当前有哪些类型
- 这些类型怎样布局
- 某些内核对象该怎样被识别

这恰好是 CO-RE 想利用的信息基础。

## 10. BTF、CO-RE、verifier 的边界分别是什么

这三者很容易被混在一起，但职责不同：

- BTF：提供类型与结构描述
- CO-RE：利用这些描述做跨内核布局适配
- verifier：在当前内核语义下证明程序安全

换句话说：

- BTF 解决“对象是什么”
- CO-RE 解决“在这台机器上偏移应当改成什么”
- verifier 解决“改完以后这样访问是否合法”

它们是互补关系，不是替代关系。

## 11. BTF 为什么会改变 BPF 的开发方式

没有 BTF / CO-RE 时，BPF 程序更容易依赖：

- 精确内核头文件版本
- 目标机现场编译
- 更重的运行时适配

有了 BTF / CO-RE 之后，开发方式更倾向于：

- 编译期记录对类型和字段的意图
- 加载期按目标内核做重定位
- 尽量减少目标机再编译需求

所以 BTF 不只是让程序“更好调试”，它实际上改变了 BPF 应用的交付模型。

## 12. 为什么说 BTF 让 BPF 更像“平台应用”而不是“内核脚本”

当一个系统具备这些能力时：

- 目标环境能自描述类型
- 程序对象能携带类型和重定位信息
- loader 能按目标环境修正程序
- 同一份逻辑能在多个内核上复用

它就开始更像一个可部署的平台应用体系，而不是“针对单一机器写死的一段内核脚本”。

这也是为什么 BTF/CO-RE 是现代 BPF 工程化的核心支柱之一。

## 13. 读 BTF 文档时建议抓住的主线

如果去读 `btf.rst` 和 `llvm_reloc.rst`，最值得抓住的是这条主线：

> 编译器把程序对类型/字段/符号的引用关系记录进对象文件，内核提供自身类型视图，libbpf 在加载时利用 BTF 和 relocation 把程序修正到当前内核布局上。

抓住这条主线后，再去看：

- type id
- string section
- func / var / datasec
- `.BTF` / `.BTF.ext`
- relocation type

这些细节就会更容易放回正确位置。

## 14. 一句话压缩版

如果把 BTF 与 CO-RE 压成一句话，可以这样记：

> BTF 为 BPF 程序和内核提供可共享的类型描述，CO-RE 利用这些描述在加载时把程序中依赖类型布局的部分重定位到目标内核的真实结构上，而 libbpf 负责把这条链路真正落地。
